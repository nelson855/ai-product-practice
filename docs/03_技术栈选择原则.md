# 技术栈选择原则

## 1. 核心结论

技术栈服务于项目学习目标和可持续实现，不追求与参考项目保持一致。后端优先级为 Java、Python、其他；前端统一优先使用 React + TypeScript。

每个项目在正式编码前必须形成独立技术栈设计，完成必要实验并由用户确认。技术选型不是一次性永久决定，但变更必须说明原因、影响和迁移成本。

## 2. 已确认偏好

| 领域 | 默认选择 | 说明 |
|---|---|---|
| 前端 | React + TypeScript | 具体采用 Vite 或 Next.js 由产品需求决定 |
| 后端 | Java + Spring Boot | P01、P02、P03 均以 Java 为第一选择 |
| Agent 学习 | Java 内显式实现 | P03 先理解 Tool、Loop、State 和停止条件，不直接依赖 LangGraph |
| Python | 条件使用 | 仅在 SDK、生态或学习目标具有明确优势时选择 |
| 其他后端语言 | 默认不选 | 必须先解释 Java/Python 无法合理满足的原因 |

## 3. 选型顺序

每个项目按以下顺序形成技术方案：

1. 明确 V1 用户流程和非目标；
2. 从参考项目提取必须支持的能力，不照搬技术栈；
3. 列出外部服务和不可控约束；
4. 设计至少一条最小纵向主链；
5. 比较 Java 方案与必要的备选方案；
6. 对高风险 SDK、流式响应、Tool Calling 或部署方式做最小实验；
7. 冻结技术栈、模块边界、数据权威和部署形态；
8. 再编写实现阶段的详细子需求。

## 4. Java 方案的判断标准

优先选择 Java + Spring Boot，前提是它能够合理完成：

- 模型和工具调用；
- 结构化输出解析；
- 流式响应或进度推送；
- 数据库、对象存储和认证集成；
- 自动化测试；
- 本地与目标部署环境运行。

AI 集成库在 Spring AI 与 LangChain4j 之间选择时，应比较：

- 所需模型和供应商支持；
- Tool Calling 与结构化输出能力；
- 流式接口；
- 可测试性和抽象泄漏；
- 当前稳定版本与维护状态；
- 是否迫使项目采用不需要的 Agent 抽象。

如果直接使用模型供应商 HTTP API 更简单、更透明，也可以不引入 AI 框架。

## 5. 何时考虑 Python

只有出现以下情况之一，才优先考虑 Python：

- 必须使用的官方 SDK 没有可用 Java 方案；
- 项目目标是学习某个 Python 原生框架的关键机制；
- Java 方案无法支持所需的模型能力或调试能力；
- Python 能显著降低验证性实验成本，且不会造成正式项目维护割裂。

即使使用 Python，也要说明它用于验证、局部服务还是整个后端，不默认形成 Java/Python 双后端。

## 6. 前端选择

默认使用 React + TypeScript：

- 纯前后端分离、无需服务端渲染时优先 Vite；
- 明确需要服务端渲染、SEO 页面或 Next.js 平台能力时再选择 Next.js；
- 不因参考项目使用 Next.js 就自动采用 Next.js；
- UI 先服务核心操作和状态表达，不提前建设复杂设计系统。

## 7. 数据和基础设施

- 数据库默认从 PostgreSQL 评估，本地轻量验证可使用兼容替代，但正式口径保持一致；
- 图片和文件通过 S3 兼容接口隔离，本地可以使用 MinIO，线上可以接 Backblaze B2；
- 外部搜索、模型和存储必须经过项目自有 Provider 接口；
- 单体应用能够满足需求时不拆微服务；
- 没有真实异步吞吐需求时不引入消息队列；
- 没有检索需求时不引入向量数据库；
- 没有长任务恢复需求时不引入持久化工作流引擎。

## 8. 技术栈设计的必要输出

每个项目的 `02_技术栈设计.md` 至少包含：

- 选型结论和适用边界；
- 原项目技术栈与自实现方案对照；
- 模块和部署结构；
- 数据权威与存储方案；
- 外部服务接口；
- 关键技术风险与验证实验；
- 未决事项和最晚确认时间；
- 明确不引入的技术及原因。
