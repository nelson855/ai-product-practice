# AI 产品实践总纲

## 1. 核心结论

本仓库通过三个递进项目，完成从 AI Feature、确定性 Workflow 到 Tool Agent 的工程实践：

| 顺序 | 自己实现的项目 | 参考项目 | 核心问题 |
|---|---|---|---|
| P01 | AI Image Mini SaaS | Backblaze AI SaaS Starter Kit | 如何把单一 AI 能力做成可使用、可部署的产品 |
| P02 | SEO Research Workflow | DAIR.AI Deep Research Agent | 哪些流程应由程序固定，哪些步骤可交给模型 |
| P03 | Keyword Research Agent | LangChain RAG Research Agent Template | 什么时候值得让模型自主选择工具和下一步 |
| P04（可选） | Deep Research Agent | darshil0/deep-research-agent 等 | 是否真的需要持久状态、恢复和复杂编排 |

统一实践路径是：

```text
运行参考项目
→ 做可回退的小实验
→ 拆解产品与架构
→ 缩减为自己的 Mini 产品
→ 讨论并冻结技术栈
→ 按阶段从零实现
→ 测试与部署验证
→ 对比和复盘
```

原始选题依据见 [01-AI_Agent开源项目仿做与实践路线.md](01-AI_Agent开源项目仿做与实践路线.md)。本文负责把路线转化为可由 Coding Agent 分阶段执行的工作体系。

## 2. 学习目标

完成三个核心项目后，应能基于实际工程证据回答：

1. 哪些能力应使用普通代码，哪些需要 LLM；
2. 一次模型调用、固定 Workflow 和 Tool Agent 分别适用于什么问题；
3. AI 产品中的认证、数据、存储、成本、错误处理和部署如何配合；
4. Tool 的输入输出、失败语义和权限为什么会影响 Agent 稳定性；
5. 何时才需要复杂状态图、Checkpoint、人工介入或 Multi-Agent。

目标不是复刻开源项目，也不是为了使用某个框架而创造复杂度。始终选择能够满足需求的最低复杂度方案。

## 3. 仓库区域约定

```text
docs/          计划、设计、子需求和学习材料
references/    上游开源项目的运行、阅读、注释和小实验区域
projects/      自己从零实现的项目
progress/      实际执行状态、阶段结果索引和阻塞记录
```

### 3.1 `references/` 可以修改

`references/` 不是只读目录。允许为了学习而：

- 添加解释性注释；
- 增加临时日志；
- 修改 Prompt、配置或少量逻辑观察效果；
- 运行小型替换实验；
- 添加不会改变研究主题的辅助测试。

修改前必须记录上游仓库地址、当前 commit SHA、工作区初始状态和启动结果。修改后使用 `git diff` 记录差异，并说明实验目的、现象和结论。未经明确要求，不提交或推送参考仓库的改动。

参考项目中的实验代码不能直接成为 `projects/` 中的正式实现。自己的项目依据产品需求、架构分析和实验结论从空目录实现；如果复制或改编代码，必须符合对应 License 和署名要求。

### 3.2 `projects/` 是正式实现区

每个项目拥有独立目录、构建方式、README 和测试。不同项目不得通过隐式文件引用形成耦合。共享代码只有在至少两个项目实际出现稳定重复后，才考虑提取。

### 3.3 `progress/` 与教材分离

`docs/` 描述计划和决策，`progress/` 记录执行事实。阶段完成后更新对应状态；未完成、受阻或未经验证的事项不能标记为完成。

## 4. 文档层级

每个项目包含三层文档：

1. `00_项目总览.md`：目标、边界、最终产品和各阶段关系；
2. `01_阶段与子需求拆分.md`：完整阶段、子需求编号、状态和依赖；
3. `phases/`：当前可执行阶段的详细子需求文档。

技术栈由 `02_技术栈设计.md` 单独维护。技术方案可以随着前置实验修订，但任何影响后续实现的变更都要先更新文档并与用户确认。

## 5. 渐进式详细设计

所有项目先建立完整阶段和子需求目录，但只把当前阶段及下一阶段写到可直接执行的详细程度。

原因是后续接口、数据结构和模块边界必须来自真实运行、源码分析和技术实验，而不是预先猜测。进入下一阶段前，应满足：

- 当前阶段验收条件已经完成；
- 未满足项明确标记为受阻或由用户接受；
- 下一阶段依赖的事实已经产生；
- 需要用户决定的产品或技术选择已经确认。

## 6. 当前已确认的技术方向

- 前端统一优先采用 React + TypeScript；
- P01、P02 后端采用 Java + Spring Boot；
- P03 先使用 Java 实现和理解 Agent 机制；
- 只有存在明确工程理由时才选择 Python；
- 如需采用 Java、Python 以外的后端语言，必须先说明必要性并取得确认；
- 具体框架版本、AI 集成库、数据库和部署方式在各项目技术栈文档中冻结。

## 8. 全部核心项目完成定义

三个核心项目只有同时满足以下条件，才算完成本实践路线：

1. 每个项目的主要用户流程可以重复运行；
2. 关键逻辑有自动化测试或可重复验证记录；
3. 技术栈、产品边界和实际实现一致；
4. 参考项目与自实现项目完成结构、复杂度和行为对比；
5. 能解释哪些决策由程序控制，哪些交给模型；
6. 能说明模型、搜索、存储和基础设施的成本边界；
7. 每个项目都有部署验证或明确的部署阻塞记录；
8. 文档记录真实结果、已知限制和后续方向；
9. 未经明确要求，不执行 Git 提交、推送、发布或生产部署。
