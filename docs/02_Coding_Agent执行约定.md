# Coding Agent 执行约定

## 1. 核心结论

Coding Agent 每次只执行一个明确编号的子需求。项目总览和阶段文档提供上下文，子需求文档决定本次工作的范围、边界和验收标准。

不得把“继续执行”“完成当前需求”解释为自动进入下一子需求，也不得因为代码可继续扩展而增加未授权功能。

## 2. 开始一个子需求

开始前依次完成：

1. 阅读项目总览、技术栈设计和阶段说明；
2. 阅读当前子需求的目标、范围、边界、依赖和验收；
3. 检查前置子需求状态和实际交付物；
4. 检查目标目录的 Git 状态，保留已有未提交改动；
5. 识别需要用户确认的产品选择、外部账户、密钥或付费服务；
6. 若前置事实与文档冲突，先报告并更新设计，不带着错误假设实现。

## 3. 执行边界

允许执行当前子需求正常需要的读取、修改、构建、测试、Lint、静态检查和本地运行。

未经当前对话明确要求，不得：

- 自动进入下一子需求或下一阶段；
- 创建、修改或删除 `AGENTS.md`；
- 启动独立 Review、Reviewer 子代理或二阶段审查；
- 执行 Git commit、amend、push、创建 PR、tag、发布或部署；
- 升级无关依赖、替换已冻结技术栈或引入额外基础设施；
- 将真实密钥、Cookie、Token、用户数据或供应商凭证写入仓库；
- 为了让验收通过而伪造外部数据、成功状态或性能结果。

正常编译、测试、Lint、静态检查、`git diff --check` 和结果核验不属于独立 Review，可以按子需求执行。

## 4. 修改参考项目

在 `references/` 中工作时：

1. 记录仓库 URL、commit SHA、分支和初始 `git status`；
2. 先完成未修改状态下的基线运行；
3. 只执行当前实验所需的最小改动；
4. 注释必须解释关键机制，不做逐行翻译；
5. 临时日志不得输出密钥、完整 Prompt 输入中的隐私数据或认证信息；
6. 记录改动前后输入、输出、耗时和错误差异；
7. 完成后报告 `git diff --stat`、关键差异和工作区状态；
8. 不自动清理、还原、提交或推送实验改动。

## 5. 正式实现原则

- 优先完成一条可运行的纵向主链，再扩展辅助能力；
- 普通代码能稳定解决的问题，不交给 LLM 决策；
- 外部服务通过项目自有接口隔离，业务代码不散落供应商 SDK 调用；
- 模型输出进入业务逻辑前必须解析和校验；
- 缺失、不确定和未采集的数据显式表达，不使用虚假默认值；
- 每个外部调用都要考虑超时、失败、限流和可观察错误；
- 不为尚未出现的规模问题提前引入微服务、消息队列或复杂编排。

## 6. 完成一个子需求

完成后必须：

1. 逐项核对验收标准；
2. 执行与风险相称的自动化测试和人工验证；
3. 记录实际命令、结果和未覆盖内容；
4. 更新该子需求和阶段状态，只标记实际完成且已验证的内容；
5. 报告新增或修改的文件；
6. 报告已知限制、外部阻塞和下一子需求的进入条件；
7. 报告目标仓库的 `git status`；
8. 停止并等待用户决定下一步。

状态只使用：`未开始`、`进行中`、`已完成`、`受阻`。

## 7. 子需求完成标准

一个子需求只有在以下条件全部满足时才能标为“已完成”：

- 范围内功能或分析产物已经形成；
- 验收条件逐项有证据；
- 适用测试通过；
- 文档与实际结果一致；
- 没有把关键未验证事项隐藏在默认值或模糊描述中。

外部 API、付费账户或真实数据缺失导致无法验收时，状态应保持“受阻”，并清晰区分已经完成的部分与仍缺少的证据。
