# P04：Deep Research Agent 启动判断

## 1. 核心结论

P04 不是默认必做项目。它只在 P03 的真实实现证明需要长任务恢复、持久状态、人工审批、复杂分支或上下文压缩时启动。

P03 如果使用简单 Java Agent Loop 已经稳定解决目标，并且任务短、失败后重跑成本低，那么停止在 P03 是正确结论，不代表实践路线没有完成。

## 2. 候选学习目标

P04 可能用于学习：

- 长时间运行的研究任务；
- Checkpoint 与恢复；
- 暂停、继续和人工介入；
- Plan 与 Replan；
- 上下文压缩和状态持久化；
- 多搜索 Provider 降级；
- 任务取消、重试和并发控制；
- PDF 等正式交付物；
- 更完整的研究产品体验。

## 3. 启动前置

必须先完成：

- P01 AI Image Mini SaaS；
- P02 SEO Research Workflow；
- P03 Keyword Research Agent；
- P03 的 Workflow 与 Agent 对比；
- P03 的部署与 LangGraph 必要性判断。

## 4. 启动信号

以下信号应来自 P03 的运行和 Eval，不得只来自理论设想：

| 信号 | 可接受证据示例 |
|---|---|
| 任务运行时间明显变长 | 常见任务跨越普通请求生命周期，重跑成本高 |
| 需要中断恢复 | 进程或网络失败后必须从中间状态继续 |
| 需要人工审批 | 某些 Tool 或高成本步骤必须等待用户确认 |
| 分支和循环难以维护 | 显式 Java Loop 已出现多个相互影响的恢复路径 |
| 上下文持续膨胀 | 真实任务触发模型上下文或费用问题 |
| 需要可靠 Replan | 搜索失败或证据冲突后必须保留已有成果重新规划 |
| 单机内存 State 不够 | 部署、并发或恢复要求需要持久化状态 |

## 5. 不启动信号

出现以下情况时不应启动 P04：

- 任务通常在短时间内结束；
- 失败后完整重跑成本可接受；
- 没有人工审批；
- State 只包含少量步骤和证据；
- P03 的主要问题来自 Prompt、Tool 或数据质量，而不是编排；
- 引入框架只能减少少量样板代码，却增加部署和调试复杂度；
- 还没有稳定 Eval，无法判断复杂框架是否带来收益。

## 6. 技术栈决策

P04 不继承“必须继续使用 Java”或“必须切换 Python”的预设。启动时单独比较：

- Java 方案是否已经能支持持久状态和恢复；
- Python/LangGraph 是否为核心学习目标提供明显优势；
- 框架的 Checkpoint、HITL、Tracing 和部署能力；
- 与现有 Java 项目集成或独立部署的成本；
- 团队熟悉度和长期维护成本。

如果选择 Python/LangGraph，必须明确说明 Java 方案不适合的具体原因，以及 Python 服务在系统中的边界。若选择其他语言，同样需要先取得用户确认。

## 7. 启动决策文档

决定启动时，先创建 `01_立项与技术栈决策.md`，至少包含：

1. P03 中触发 P04 的真实问题；
2. 不引入复杂编排时的替代方案；
3. Java、Python/LangGraph 和其他候选方案对比；
4. 只解决一个核心问题的 V1；
5. 阶段、子需求、成本和停止条件；
6. 如何证明 P04 比 P03 更好，而不是仅仅更复杂。

该文档由用户确认后，才生成 P04 的阶段与子需求合集。
