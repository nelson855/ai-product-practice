# 阶段切换与子需求设计规范

## 1. 目的

本规范解决两个问题：

1. 当前阶段完成后，如何让 Coding Agent 设计下一阶段的详细子需求；
2. 下一阶段设计完成后，如何让 Coding Agent 执行其中一个子需求。

项目只预先写完整阶段路线和子需求清单。当前阶段的详细文档完成后，才根据真实结果展开下一阶段的详细文档。

## 2. 三种操作必须区分

| 操作 | 目标 | 是否写代码 |
|---|---|---|
| 阶段验收 | 判断当前阶段是否真的完成 | 通常不写 |
| 下一阶段设计 | 根据真实产物生成下一阶段详细子需求 | 不写正式实现代码 |
| 执行子需求 | 实现或完成一个已定义的子需求 | 按子需求要求 |

“下一阶段设计”不能自动等同于“开始实现下一阶段”。

## 3. 推荐的最短指令

### 3.1 请求阶段验收

```text
请按项目文档验收 P01-S01，先不要进入下一阶段。
```

### 3.2 请求下一阶段子需求设计

```text
请按项目阶段推进规范，进入 P01-S02 的子需求设计。
```

将 `P01-S02` 替换为目标项目和阶段编号，例如 `P02-S02`、`P03-S03`。

### 3.3 请求执行当前子需求

```text
请按项目文档执行 P01-S02-01，完成验证后停止。
```

### 3.4 请求继续当前阶段

```text
请按项目文档继续当前阶段，先执行下一个未完成的子需求，完成后停止。
```

如果当前阶段没有已生成的详细子需求，Agent 必须先报告“需要进入阶段设计”，不能直接猜测实现内容。

## 4. Agent 进入下一阶段设计时必须执行的步骤

当用户请求“进入 `<项目>-<阶段>` 的子需求设计”时，Agent 必须：

1. 阅读 `../00_实践总纲.md`、`../02_Coding_Agent执行约定.md` 和项目总览；
2. 阅读项目的技术栈设计与阶段拆分文档；
3. 阅读当前阶段的所有详细子需求和实际执行结果；
4. 检查当前阶段的每个子需求状态、验收证据和遗留问题；
5. 判断目标阶段的前置条件是否满足；
6. 检查参考项目、代码、运行报告、测试和 Git 状态中的真实事实；
7. 提取目标阶段必须解决的问题和不能继续沿用的假设；
8. 确定目标阶段的子需求数量、依赖和可并行内容；
9. 为每个子需求创建独立 Markdown 文档；
10. 按 [子需求文档模板](../04_子需求文档模板.md) 写目标、输入、范围、边界、交付物、验收和验证方式；
11. 标记仍需用户确认的技术、产品、外部服务或费用事项；
12. 只更新文档和阶段状态，不实现正式代码；
13. 报告是否满足进入条件、创建的文档、阻塞事项和 Git 状态，然后停止。

## 5. 进入条件不满足时

如果当前阶段存在未完成子需求、缺少关键运行结果、未完成验收或重要设计冲突，Agent 不得直接设计下一阶段的确定性实现方案。

此时应：

- 说明具体缺口；
- 区分“可以提前准备”的工作和“不能替代前置验收”的工作；
- 如果用户明确要求，可以创建标记为“待前置确认”的草案，但不能把草案当成可执行方案；
- 给出完成前置条件所需的最短下一步。

## 6. 子需求设计的内容要求

每个子需求必须能够独立交给 Coding Agent，并至少包含：

- 稳定的编号和名称；
- 所属项目与阶段；
- 当前状态；
- 目标和用户价值；
- 真实输入和前置产物；
- 实现范围；
- 明确边界和不做事项；
- 技术与执行要求；
- 交付物；
- 正常和失败验收标准；
- 自动化测试、人工验证或实验方法；
- 未决事项和停止条件。

不得使用“完成整个后端”“完善 Agent”“处理相关问题”等无法独立验收的任务名称。

## 7. 设计阶段的范围限制

进入下一阶段设计时：

- 可以读取、分析和补充项目文档；
- 可以根据真实代码和运行结果修正下一阶段计划；
- 可以创建阶段说明和子需求文档；
- 不得自动实现下一阶段代码；
- 不得自动提交、推送、创建 PR、发布或部署；
- 不得修改 `../../AGENTS.md`，除非用户明确要求维护项目代理文档；
- 不得启动独立 Review 或 Reviewer 子代理。

## 8. 阶段设计后的执行方式

阶段文档生成后，用户可以选择一个子需求执行。执行时 Agent 必须只阅读并执行当前子需求，完成适用验证，并报告：

1. 修改或创建的文件；
2. 执行的命令和结果；
3. 验收标准逐项结果；
4. 未验证条件和已知限制；
5. 下一项的进入条件；
6. Git 工作区状态。

完成一个子需求不代表阶段自动完成。阶段需要单独验收，阶段验收通过后再进入下一阶段设计。

## 9. 推荐状态流转

```text
未开始
  ↓ 用户请求执行
进行中
  ├── 验收满足 → 已完成
  └── 外部条件缺失/无法验证 → 受阻

当前阶段全部子需求完成
  ↓ 阶段验收
允许进入下一阶段设计
  ↓ 用户请求
生成下一阶段详细子需求
  ↓ 用户确认或直接指定执行
执行下一阶段子需求
```

## 10. 输出格式

阶段设计完成后，用简短结果报告，不重复粘贴所有文档内容：

```text
目标阶段：P01-S02
进入条件：满足 / 不满足 / 部分满足
新增文档：列出路径
主要设计结论：列出关键点
待用户确认：列出影响实现的事项
阻塞：没有则写“无”
Git 状态：列出状态
```

## 11. 与已有项目文档的关系

- 项目总览说明目标和边界；
- 阶段拆分说明完整路线、依赖和状态；
- 技术栈设计说明技术选择及其确认点；
- 本规范说明何时生成详细子需求以及如何执行；
- 单个子需求文档说明本次具体工作和验收条件。

如果这些文件互相矛盾，Agent 必须先报告冲突，不得自行选择一个版本静默实现。
